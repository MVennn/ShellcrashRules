# release-notes/

> **一句话**：这里放面向使用者的 Release 说明 —— 一版一份，文件名 = 版本号，
> 写成清单（不是文章），末尾带固定尾巴。

放**面向使用者**的 Release 说明，文件名 = 版本号：

```
docs/release-notes/v0.1.0.md
```

版本号规则以 [VERSIONING.md](../VERSIONING.md) 为**唯一正本**（三段式进位）。
本篇只管**格式**。

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：症状 / 根因 / 改法 / 验证结果 / 实测数字。
Release 说明是**给使用者看的**，要短、写成清单、只讲「这一版现在是什么样」。
两者受众不同，不能一份两用。

## 形状

**清单，不是文章。** 开头一句加粗说清这版是什么，`## 本版内容` 下按分区一行一条，
最后是固定尾巴。

```markdown
**新增 CN 直连中间层与全局 QUIC 阻断；规则生成器改为每周自动更新并带校验。**

## 本版内容

**分流规则**

- 调整 CN 直连中间层 —— 在生成配置里把 `RULE-SET,cn` 插到电报规则之后、国外媒体之前，宽泛代理不再抢 CN 域名。
- 新增 分类修正层 —— 修正模板里 Bing / googleapis / OneDrive 等过宽规则，改走 微软服务 / 节点选择。

**防火墙**

- 新增 全局 QUIC 阻断 —— `quicguard.nft` 拒 UDP 443/8443 等，浏览器回落 TCP，Google 端点不再带国内出口 IP 直出。

**工具**

- 新增 规则审计 —— `tools/rule_audit.py` 离线算每条域名规则的真实生效目标，输出遮蔽与误伤清单。

---

适用范围：小米 AX3000T（OpenWrt 25.12）+ ShellCrash + mihomo v1.19.32（Redir 模式）。
本仓库不随分发机场订阅凭据、节点 UUID 或路由器口令。
```

结尾那两行适用范围说明是**固定尾巴**，每版照抄不动。
它是固定尾巴的一部分，**不算重复内容**。

### 一条怎么写

```
新增 / 调整 / 修复 / 优化 + 对象 —— 一句话说明
```

- **动词只有四个**：新增（以前没有）、调整（行为、默认值、位置变了）、
  修复（以前不对，**含底层与实现层**）、优化（用户能感知的更快 / 更小 / 更顺）。
- **对象照抄实物名**：策略组名（`🤖 AI接口`）、文件路径（`config/yamls/user.yaml`）、
  规则动作（`RULE-SET,cn`）、脚本段（`rules-mid.sh`）、nft 表名。
  **不加引号书名号**，也不另起一个说法。
- **一句话说完**，写使用者拿到什么。不写怎么用、不写为什么。
- 说人话。「SNAT」「conntrack」「YAML 重复键」这类只对实现者有意义的词别写；
  真要交代限制，写看得见的后果（「配置被拒载时全部自定义分组会消失」）。
- 一行一条。两句才说得清 → 拆成两条，或者这条本来就该留在 CHANGELOG。

## 底层与内部改动：算「修复」，而且要拆开写

这条是给「使用者看不出区别、但确实改了」的改动定的。**它们也算本版内容，
必须写；而且要一条一条拆开，不许打包成一句。**

| 改了什么 | 动词 | 一行怎么写 |
|---|---|---|
| 底层缺陷（重复键、路径写错、校验缺失、竞态） | 修复 | 写「以前会怎样」的后果，不写根因 |
| 重构 / 拆文件 / 收敛依赖（行为零变更） | 修复 | `修复 代码拆分 —— 哪几处拆开，行为零变更` |
| 删死代码、删悬空配置、清理失效规则 | 修复 | `修复 死配置 —— 删了哪几处，行为零变更` |
| 口径纠错（文档与实现不符） | 修复 | 写纠了什么口径，不写讨论过程 |
| 仓库结构（新增文档、归档、拆分目录） | 调整 | `调整 仓库 —— …`；使用者不可见的也照写 |
| 使用者能感知的更快 / 更小 / 更顺 | 优化 | 写「快在哪」，并给数字（规则条数、耗时、体积） |

**禁止写法**：

- ❌ `优化 代码整理 —— 按职责拆分、依赖收敛，行为零变更`
  —— 三个改动压成一句，对不上 CHANGELOG，下个版本没人知道拆了哪些文件；
- ❌ `优化 稳定性 —— 高危 3 条、低危 10 条全部清零，细目见 CHANGELOG`
  —— 「细目见 CHANGELOG」等于没写；
- ✅ 拆成 4~6 行，每行一个对象，行尾该标「行为零变更」的就标。

一句话记法：**凡是在 `git diff` 里出现过的东西，说明里都要有一行**。
写不长不是本事，漏了才是问题 —— 篇幅红线排在覆盖率之后。

## 覆盖率红线

**凡本版改过的东西，必须全部出现在 Release 说明里**，动词四选一（新增 / 调整 /
修复 / 优化），一行一条。没有例外：

- 排查出的真缺陷与修复 → 并进「修复」分组，一行写「修了什么 + 看得见的后果」
- 规则 / 分流调整 → 并进「调整」或「新增」分组
- 纯重构（行为零变更）→ 并进「修复」分组，**按对象拆成多行**
- 文档 / 声明类（README、NOTICE、DOC-RULES）→ 并进「仓库」分组，照写

写完拿 CHANGELOG 对应段落逐条对：**CHANGELOG 里的每一处改动，
Release 说明里都得能找到对应行**。

### 篇幅

- 覆盖率红线优先于篇幅：先保证**一条不漏**，再谈合并。
- 分组按本仓的目录走（分流规则 / 防火墙 / 工具 / 仓库），不按轻重排。
- 合并手法：同类项归并成一行但列出对象；审查修复写用户可见后果，不写根因长文。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称叙述（「你可以先跑一下…」「想换的话…」） | 使用者要的是有什么，不是操作步骤；步骤归 README |
| 「原来是这样，所以现在…」的原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、匹配算法、字段来源 | 同上 |
| 开关默认开还是关、改完要不要重启 | 通用信息，不随版本变 |
| 「之前是什么样」的对比 | 只有修复条目允许一句症状（「全部自定义分组消失」），其余不写 |
| 「本版没有破坏性变更，直接覆盖安装」 | 没变更就不用声明；**有**的时候才必须写 |
| 凑数的「注意」区块 | 见下 |

## 「注意」区块：能不写就不写

只在**使用者不知道就会出问题**时才写，最多一两条：

- ✅ **有破坏性变更** —— 目标路径变了、要重新部署、配置会丢。**必须写**。
- ✅ **已知的、会被当成新 bug 的问题** —— 例如某个组目前是空的、某个探测需要额外工具。如实写一条，
  免得被重复报。
- ❌ 每版都一样的操作提醒、性能说明 —— 不写。适用范围说明**例外**：
  每版说明末尾固定附适用范围段，**逐字粘贴**，属固定尾巴，不算重复内容。

## 改已经发出去的说明

写完 `docs/release-notes/v<版本>.md`、递增版本号、推一个同名 tag
（`v<版本>`）即可发版。已发出去的说明要改，直接改文件再重发同一个 tag ——
**不要**新建一个版本号来掩盖措辞问题。

- [ ] 一行一条，一行不超过两行
- [ ] 结尾固定尾巴逐字粘贴
- [ ] CHANGELOG 里每处改动都能在说明里找到对应行
